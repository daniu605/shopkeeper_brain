# 问器知识库（Shopkeeper Brain）

> 面向商品/设备技术文档的 RAG（检索增强生成）智能问答系统。

**项目说明**：本仓库是作者根据**实习期间参与的 RAG 智能知识库项目**经验，独立完成的仿制复刻项目。整体架构思路、检索链路设计来源于实习项目的真实工程实践，所有代码由本人独立实现与调试，用于系统性地沉淀和展示 RAG 全链路的工程能力（文档处理 → 混合检索 → 多路召回 → 融合重排 → 流式生成 → 多轮对话）。

---

## 一、项目能做什么

用户上传产品手册（PDF/Markdown）后，系统自动完成「文档解析 → 切片 → 向量化 → 入库」；之后用自然语言提问，系统通过「商品确认 → 多路检索 → 融合重排 → 流式生成」给出基于知识库的答案，并支持联网搜索兜底与多轮对话上下文理解。

| 能力     | 说明                                                |
| ------ | ------------------------------------------------- |
| 文档智能导入 | PDF/MD 上传后异步处理，前端实时展示各节点进度与耗时                     |
| 混合向量检索 | BGE-M3 稠密（语义）+ 稀疏（关键词）双路，Milvus WeightedRanker 融合 |
| 三路并行召回 | 向量检索 ∥ HyDE 假设文档 ∥ MCP 联网搜索，扇出-扇入拓扑               |
| 智能重排序  | BGE-Reranker 精排 + 断崖检测动态截断                        |
| 流式问答   | SSE 长连接，progress / delta / final 三类事件逐字推送         |
| 多轮对话   | MongoDB 会话历史 + LLM 指代消解改写（"它的电池怎么换"能听懂）           |
| 优雅降级   | 每个环节均有防御性取值与降级策略，单点故障不阻断整条流程                      |

## 三、核心逻辑与设计思路

本节说明各核心模块的实现方式与设计依据。

### 3.1 导入流水线：非结构化文档到可检索知识的转换

**LangGraph 状态图编排 7 个节点**，入口用条件边区分 PDF / MD 两条路径，在 `md_img` 节点汇合后再走统一流程：

1. **PDF 转 Markdown（MinerU）**：复杂排版（表格、公式、图片）解析为 MD + 独立图片文件；
2. **图片处理（VLM）**：图片上传 MinIO，用视觉模型生成图片描述并替换 MD 中的引用，让"看图才能理解的内容"也可被检索；
3. **文档切分**：三级策略——先按 Markdown 标题一级切分保留语义边界；超长块按段落/句子/字符二次切分并**贪心装箱**；过短块按父标题**智能合并**。每个 Chunk 携带 `title / parent_title / part` 等溯源元数据；
4. **商品名识别（LLM）**：从文档标题与首部切片提取商品名并回填所有切片。这是后续按商品过滤检索的前提，避免不同设备的同名实体互相污染；
5. **混合向量化（BGE-M3）**：单模型一次编码同时产出 1024 维稠密向量与稀疏词权重，入库时稠密用 COSINE、稀疏用 IP 建索引；
6. **Milvus 入库**：支持"拆旧重建/新建/复用"三种集合策略，幂等导入——同一文档重复导入不会产生脏数据。

### 3.2 查询流水线：一次提问背后的完整链路

同样用 LangGraph 编排，`multi_search` / `join` 为虚拟节点实现扇出-扇入，三路检索并行执行。

#### （1）商品名确认 —— 解决"多轮指代 + 跨商品串扰"

节点内部按职责拆成 4 个组件（历史管理 / LLM 提取 / 向量检索 / 评分对齐）：

- 从 MongoDB 取最近 10 条历史，格式化为 `role: text` 注入提示词；
- LLM 以 **JSON 结构化输出**同时完成两件事：提取商品名 + **问题改写**（把"它的电池怎么换"改写成独立完整的"RS-12 万用表怎么换电池"）；
- 提取出的商品名经 BGE-M3 向量化后，在 Milvus 商品名集合上做混合检索对齐；
- **双阈值评分对齐**：score ≥ 0.7 且与 LLM 结果互含 → 直接确认；0.6~0.7 → 转为候选让用户选择；< 0.6 丢弃。多个确认结果间再按**分数差 > 0.15 剔除误判**；
- 三种出口路由：确认成功 → 走检索；模糊 → 返回候选列表请用户选择；皆无 → 友好提示。

**设计取舍**：阈值偏严宁可多问一句，也不把答案导向错误商品——误直认的代价远大于一次确认交互。

#### （2）三路并行召回 —— 单路检索总有盲区

| 路径       | 解决什么问题                                                                                                                      |
| -------- | --------------------------------------------------------------------------------------------------------------------------- |
| 向量检索     | 常规语义匹配，主路                                                                                                                   |
| HyDE 检索  | 问题太短/口语化时，先让 LLM 生成一段"假设性技术文档"再去检索——假设文档包含更多关键词与上下文，召回质量更高。细节：生成的假设文档按 HyDE 原论文用**文档编码器**（`is_query=False`）编码，与库内切片处于同一语义空间 |
| MCP 联网搜索 | 知识库未覆盖的问题兜底，走百炼 web_search 工具                                                                                               |

#### （3）RRF 倒数排名融合 —— 基于排名的异构检索结果融合

三路检索的分数量纲不同（余弦相似度、rerank 分、网页相关性），直接加权比较没有意义。RRF 只用**排名**打分：

```
score(d) = Σ  weight_i / (k + rank_i(d))    # k=60，向量路 0.5，HyDE 路 0.3
```

同一切片在多路中出现时贡献相加——"多路互证"的切片天然排前面，这正是融合的价值。

#### （4）Rerank 重排 + 断崖检测 —— 保留条数由分数分布动态决定

- 本地切片与网页结果先统一为通用 doc 格式（`source/content/title/url`），一起送入 BGE-Reranker 打分；
- **断崖检测动态截断**：按分数降序后，找到第一处相邻分数差 > 0.15 的"断崖"，断崖后的视为噪声文档直接丢弃；同时兜底约束至少保留 2 条、至多 5 条；
- 降级策略：重排器打分失败时全部置 0 分，稳定排序保持原始顺序（本地在前、网页在后），流程不中断。

#### （5）答案生成 + SSE 流式输出

- 重排后的文档格式化为带元数据的参考上下文，连同历史、商品名注入 `ANSWER_PROMPT`，约束 LLM **只基于参考内容回答**；
- LLM 逐 chunk 流式生成，每个增量实时推入 SSE 队列（`delta` 事件），结束推 `final` 事件；
- SSE 消费端用 `run_in_executor` 包装阻塞队列读取避免卡事件循环，主动探测客户端断连，`finally` 中清理队列防止内存泄漏。

#### （6）多轮对话 —— 无状态图 + MongoDB 外部记忆

LangGraph 图本身不存会话状态（未用 checkpointer），每轮问答结束后由 `answer_output` 将 user / assistant 两条记录写入 MongoDB `chat_message` 集合；下一轮提问时由 `item_name_confirm` 按 `session_id` 取最近 10 条（ts 降序取回后反转为升序），注入上述两个提示词完成上下文衔接。商品名首次确认后还会做**纯内存回填**（只改已取出的记录，不写库），不污染历史数据。

> 这样设计的收益：会话随 MongoDB 持久化，服务重启不丢、多实例部署天然共享；代价是历史长度受 limit 截断，超长会话存在上下文压缩空间。

### 3.3 工程化设计

- **分层架构**：API 层（FastAPI 路由）→ Service 层（任务编排）→ Processor 层（LangGraph 图）→ Utils 层（客户端/工具），职责清晰；
- **依赖注入 + 缓存单例**：`core/deps.py` 统一管理服务实例，客户端（LLM/Milvus/Mongo/MinIO）经双重检查锁懒加载；
- **延迟导入**：重依赖（模型、SDK）全部在函数内 import，服务启动秒级完成；
- **防御性编程与降级**：每个节点统一继承 `BaseNode`（校验 → process → 日志），字段缺失有兜底值、外部调用失败有降级路径，任何单点失败都不阻断主流程；
- **全链路可观测**：节点级日志 + 任务状态追踪（`done_list / running_list / durations`），前端可实时展示每个节点的执行进度与耗时。

## 四、技术栈

| MCP                | 标准化协议接入第三方联网搜索工具                 |

## 五、快速开始

**环境要求**：Python 3.12、NVIDIA 显卡（可选，GPU 加速）、CUDA Toolkit 12.8（MinerU VLM 与向量模型需要）

1. **安装依赖**
   ```bash
   cd knowledge
   pip install -r requirements.txt
   ```
2. **配置环境变量**：复制 `.env` 并按实际情况填写：
   - `DASHSCOPE_API_KEY` / `OPENAI_API_KEY`：DashScope 密钥
   - `MILVUS_URL` / `MONGO_URL` / `MINIO_ENDPOINT`：存储服务地址
   - `BGE_M3_PATH` / `BGE_RERANKER_LARGE`：本地模型路径
   - `BGE_DEVICE=cuda:0`：向量模型运行设备
3. **准备存储服务**：启动 Milvus、MongoDB、MinIO（可用 `knowledge/test/import_process/测试存储服务器是否启动成功.py` 一键验证）

**启动导入服务**（端口 8000）：

```bash
set PYTHONPATH=E:\shopkeeper_brain\shopkeeper_brain
knowledge\.venv\Scripts\python.exe knowledge\api\import_router.py
```

浏览器打开 `http://127.0.0.1:8000/import.html`，上传 PDF/MD 即可实时查看节点进度。

**启动查询服务**（端口 8001）：

```bash
knowledge\.venv\Scripts\python.exe knowledge\api\query_router.py
```

浏览器打开 `http://127.0.0.1:8001/chat.html`，输入问题即可获得流式答案。

## 六、核心 API

| 服务 | 接口                                     | 说明                               |
| -- | -------------------------------------- | -------------------------------- |
| 导入 | `POST /upload`                         | 上传文件，返回 task_id                  |
| 导入 | `GET /status/{task_id}`                | 导入节点状态轮询                         |
| 查询 | `POST /query`                          | 提交问题（流式返回 task_id，非流式返回答案）       |
| 查询 | `GET /stream/{task_id}`                | SSE 长连接（progress/delta/final 事件） |
| 查询 | `GET /history/{session_id}` / `DELETE` | 历史加载 / 清空                        |
| 通用 | `GET /docs`                            | Swagger 交互文档                     |

每个节点文件都带 `__main__` 测试块（如 `bge_embedding.py`、`rrf.py`），可单独运行验证。
